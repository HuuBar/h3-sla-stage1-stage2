# MiniMax-H3 上 SLA 稀疏训练技术报告

> 整理时间:2026-08-24 | 范围:音频文本稀疏计划(开放竞争 vs 列保护)的方案、实测与训练进展
> 相关文档:`h3_sla_training_log.md`、`sla_ref/h3_sla_training_plan.md`、`sla_retrain_plan.md`

---

## 1. 背景与目标

**模型**:MiniMax-H3 —— 33B 音视频联合生成 DiT(50 层,hidden 5376,56 heads × head_dim 128)。文本、视频、音频 latent token 被打包进**同一条序列**做共享注意力。

**问题**:768p 训练/推理时单条 packed 序列约 **3.8 万 token**(视频 37296 + 音频 414 + 文本 ~390)。注意力 O(N²) 是全流程最大瓶颈,需要稀疏化。

**方案**:采用 SLA(Sparse-Linear Attention, arXiv:2509.24006)——块级稀疏注意力,目标省掉约 **95%** 的注意力计算,并通过少量全参微调让模型适应稀疏化。

---

## 2. SLA 原理(简述)

SLA 把注意力拆成两个分支之和:

- **稀疏分支**:把 query/key 按块(64×64)mean-pool 成块表示 → 块间打分(带 smooth-k 技巧)→ 每个 query 块只对 top-k 个 key 块做精确 softmax 注意力。k 由全局比例 `topk_ratio` 决定(`topk = int(0.05 × 总块数)`)。
- **线性分支**:φ(q)(φ(k)ᵀv) 形式的线性注意力,输出经一个**可训练投影 `proj_l`(零初始化)** 加权,训练中逐步学习补偿稀疏分支丢失的信息。

训练起点 = 纯稀疏注意力(proj_l=0),模型只需少量步数即可适应。推理侧可用 SLA 省掉 ~95% 的注意力计算。

**本实现的配置**:topk=0.05、feature_map=softmax、blk_q=blk_k=64、head_dim=128、proj_l fp32 零初始化。

---

## 3. H3 双模态挑战:文本/音频 token 极易被稀疏淘汰

H3 的 packed 序列中 **~97.8% 是视频块**:

| 模态 | token 行数(768p) | key 块数(64/块) | 占比 |
|---|---|---|---|
| 视频 | 37296(固定) | 583 | 97.8% |
| 音频 | 414(207 帧 × 2ch) | ~7(含混合块) | ~1.2% |
| 文本 | 25~632(p50=390) | ~6(含混合块) | ~1.0% |
| 合计 | ~38090 | **K≈595/596** | 100% |

**含文本/音频的 key 块仅 13 块(2.2%)**。朴素块稀疏按得分选块时,极少数文本/音频块极易被淘汰 → **文本条件丢失、音画同步破坏**。这是本计划要解决的核心问题。

---

## 4. 核心问题实测:开放竞争 vs 列保护

### 4.1 开放竞争(纯全局 top-0.05,无任何保护)

在原始权重 + prompt 的完整 50 步推理轨迹上,用真实 meanpool 打分 + 每 query 行 top-29 选择(共 2500 次注意力调用)实测:

| 指标 | 实测值 |
|---|---|
| 每 query 行选中的文本/音频块数(均值) | **2.427**(min 0 / max 13) |
| 选中 0 个文本/音频块的 query 行占比 | **57.58%** |
| 行间并集(13 块至少被 1 行选中) | **13/13(100%)**,且 50 步全程保持 |
| 对应稀疏度 | **0.9513**(1 − 29/595) |

**结论**:
- 文本/音频块的 meanpool 得分并不低——每行平均 2.4 块入选,高于"得分与模态无关"的均匀期望(0.63),部分行甚至选满 13 块。
- 但**仍有 57.6% 的 query 行一个文本/音频块都看不到** → 这些行的输出完全接触不到文本/音频条件,文本条件丢失、音画同步破坏的风险真实存在。
- 早期步(高噪声)更严重:第 1 步行均值仅 ~0.3–0.5 块。

### 4.2 列保护(force-critical)

把含文本/音频的 13 个 key 块对**所有 query 行强制可见**(块分数置 +inf,topk 相应扩大):

| 指标 | 值 |
|---|---|
| 每行选中块数 | 29 + 13 = **42** |
| 稀疏度 | **0.9294**(实测与理论一致) |
| 文本/音频可见性 | 所有层、所有步、所有 query 行 **100%** |

**代价**:稀疏度从 95.1% 降到 92.9%(多算约 2% 的注意力),换来文本/音频条件恒定在场。

### 4.3 稀疏选择的动态特性

- 块选择**每步、每层、每 query 行独立重算**(打分来自当步 q/k,随去噪轨迹变化)。
- 早期步选择接近随机、后期步由内容驱动趋于稳定。
- 列保护 = 全部 50 步中的"静态锚点":13 个文本/音频块全程被选;其余 582 个视频块动态轮换。

## 5. 训练方案与历程

### 5.1 数据来源

数据经历了**两条路线**,最终采用"生成 latent"路线:

**路线一:真实视频(8/11–8/12,480p)**
- 来源:YouTube 片段。自建 IR5k 清单(`dl_list_ir5k.jsonl`,4724 条计划 → 实际下载 4462 条),字段含 `vision_cap / audio_cap / subtitle / vast_cap` 等标注,`vast_cap`(画面+声音综合描述)直接可用作 H3 prompt。
- 处理:yt-dlp 下载 → ffmpeg 校验时长 ±0.5s → 抽 2ch 32kHz 音频 wav → 生成 metadata(video / input_audio / prompt 三列,一一对应,硬约束"不足 5000 条没关系")。
- prompt 清洗:先规则清洗(8/12 定案用纯文本增强重写,不用 VLM 关键帧方案)。
- 缓存:`data_process` 用 text encoder / video VAE / audio VAE 把视频、音频、prompt 编码成 latent 缓存(480p:video latent `[1,24,37,30,52]`);2000 条 / 3600 条两个版本。
- 质量核查:全量扫描白屏中位 2.6%、cache 解码 0–7.4% → 数据本身不白。

**路线二:生成 latent(8/17 起,当前路线)**
- 动机:训练数据不足/真实视频质量波动,用户定案用 **FL2VA 原始权重 50 步推理生成 768p latent** 当训练数据(标准扩散 SFT,非蒸馏)。
- 产出:`ir5k_gen_latent_cache_768p`(2493 条),后经 stage2 预处理(`use_gradient_checkpointing=True`)成为当前训练集;另有 2000 条 480p 版本用于过渡。
- 当前训练:768p latent 2493 条,16 卡 batch=1/rank → **156 步/遍**;超参主干 lr 1e-5 / proj_l 5e-5,1 epoch,flow-matching SFT 损失。

### 5.2 为什么调整训练策略、怎么调整的

**问题:两轮 480p 微调都训出"偏白/白屏"**,且越训越白(SLA 推理 78.8%)。通过判别实验三连 + 采样轨迹 + velocity 探针,把根因钉死为一条完整链条:

```
训练火力分布缺陷(shift=12 下均匀采 timestep → σ<0.2 低噪端只占 ~2% 火力
  + BSMNTW 损失权重在低噪端仅 0.21–1.7)
→ 全参微调主干漂移 ~0.1%(lr 1e-5 的数学必然)
→ 低噪端对权重漂移敏感(σ→0 时模型靠 timestep 精确落位,敏感度是中段 2.5–2.7 倍)
→ 最后一步 velocity 过冲 → latent 冲出 VAE 正常范围 → 解码全白
```

**调整历程**:

| 轮次 | 策略调整 | 效果 |
|---|---|---|
| 第一轮(2000 条) | 全范围均匀采样、无 clip-grad | 白 78.8%(SLA 推理) |
| 第二轮(3600 条) | **混合采样**(50% 走低噪段 min-boundary 0.77)+ **clip-grad 1.0** + 从原始权重重训 | 白降到 52.3%,缓解未根治(教训:低噪段边界没选到 σ<0.2 真正所在区) |
| 修正方向(8/15 提出) | A:低噪采样收窄到 σ≤0.2/0.3 且段内均匀采样;B:lr 1e-5→5e-6 降主干漂移 | 待执行,后被生成 latent 新路线取代 |
| 生成 latent 路线(8/17) | 训练数据换成 FL2VA 生成 latent;proj_l 初始化定案为 **0**(不再注入 0.0053) | 480p 50 步跑通 |
| 768p stage2(8/19–8/24) | 768p 全参微调,156 步 → step-156(保护版) | sparsity 0.929 |
| **当前轮(开放竞争,8/24)** | 从 step-156 续训 156 步,`SLA_FORCE_OFF` 去掉列保护(纯 topk 0.05),每 40 步存 ckpt | 训练中 |

### 5.2.1 两阶段方案:阶段一(proj_l 逐层对齐,8/17 定案、8/18 跑通)

阶段一的目标是**主干零漂移地先把 proj_l 训到位**:冻结 DiT 主干全部参数,仅保留每层注意力中新增的线性补偿投影 proj_l(50 × 128×128,≈0.83M 参数)可训练;AdamW 仅含 proj_l 参数组,lr=1e-4,共 200 步。实现上采用**单卡 + CPU offload**(未用 ZeRO-3:主干冻结(bf16)与仅 proj_l 有梯度(fp32)的混合精度组合会触发 deepspeed 0.19.4 的梯度分桶断言错误,16 卡方案不可行;proj_l 仅约 3MB,单卡即可承载)。

数据为 480p 生成 latent 缓存 200 条(单卡 batch=1),时间步从 50 步推理网格采样(shift=12),使训练分布对齐推理分布。每层同时计算两条路径的输出:稀疏注意力路径(块稀疏选择 + proj_l 线性补偿)与稠密注意力路径(同一份 q/k/v 的完整注意力);稠密输出作为该层对齐目标,主干冻结使其全程恒定,回归问题平稳。训练采用**两遍法**:第一遍全程 no_grad,将各层两条路径的输出抓取存至内存(显存降至推理级,约 10.9GB);第二遍仅对 proj_l 分支重建逐层小计算图,逐层计算 MSE、逐层独立 backward,图即用即毁。相比输出级 SFT 损失,梯度直达 proj_l、不被 48 层主干稀释(输出级路径梯度实测衰减至 ~1e-6,proj_l 收不到有效梯度);相比整图反传,单卡 + CPU offload 下参数搬运抖动严重(实测首步 35 分钟未完成),两遍法约 19 s/it。

结果:200 步约 64 分钟,产物仅 proj_l 权重(100 keys,3.3MB),主干零漂移(保持原始 FL2VA 权重);proj_l mean|w| 自 0.0001 单调增长至约 0.005(训练有效性判据;逐层对齐损失本身大幅震荡,系各层/各 timestep 差异的固有噪声,不作收敛判据)。该 proj_l 随后转为 safetensors,与原始 13 分片同包,作为阶段二(主干 lr 1e-5 / proj_l 5e-5 双 lr 联合微调)的起点,即 §5.5 中 proj_l 续训值的来源。

### 5.3 从 480p 到 768p

- **latent 尺寸差异**:480p 为 `[1,24,37,30,52]`(token 57720),768p 为 `[1,24,37,48,84]`(token 149184)——分辨率翻倍导致序列近 3 倍。
- **过渡期裁剪方案(8/17)**:768p latent 显存放不下 → 先**中心裁剪成 480p**(H 48→30、W 84→52)。关键坑:只裁 input_latents 会 `index_copy` 错位崩(img_pos 37296 vs video_rows 14430),必须用 pipeline 原生打包器**重建 packed 序列**(seq_len/img_pos/audio_pos/text_pos 与 data_process 一致)。
- **正式上 768p(8/19)**:配合 CPU offload(见 5.4)与 ckpt 缓存字段修复,768p 直接在 16 卡上训练,不再裁剪。

### 5.4 OOM 问题与解决(三层)

| 层 | 现象 | 根因 | 解决 |
|---|---|---|---|
| 缓存层 | 生成 latent 训练 32 层全激活 49GB 必爆 | 缓存 `.pth` 内嵌 `use_gradient_checkpointing=False` 覆盖 CLI | **批量改缓存字段为 True**(不依赖 CLI,缓存才是真源) |
| 显存层 | 768p(149184 token)+ zero3 无 offload 必崩 | 序列太长,单卡放不下 | **zero3 CPU offload 配置**(param/optimizer offload 到 CPU)+ 每步 `zero_grad()` 后 `empty_cache()`;实测 HBM 归零、AICore 满算力,代价每步 ~92–104s |
| SLA 反向层 | 训练 18/125 步 NPU OOM(50.2GB) | Triton backward 数值损坏改 **torch 重算** 后 fp32 全尺寸 dq/dk/dv(≈436MB/层 × 48 层)+ force_mask 张量 | head 分组 HG=8 + query chunk CH=8 防 OOM;反向固定用 torch 重算路径 |

### 5.5 当前训练状态(2026-08-24)

- 已验证:模型确实以 **SLA + 开放竞争** 运行(tensorboard `sla_sparsity = 0.9513`,与理论值一致;保护版应为 0.9294)
- **proj_l 为续训值**(从 step-156 加载,mean|w|=0.00528,100% 非零;无外部注入/重新初始化)
- loss 正常下降区间(~0.46),0 错误
- 预计 step-40/80/120/156 四个 ckpt(约 66GB/个)依次落盘

## 6. 性能与代价

| 模式 | 每步耗时(768p, 16 卡 offload) | 说明 |
|---|---|---|
| 稠密全注意力 | ~133 s/it | NPU 原生 FlashAttention,算子极度优化 |
| SLA 保护版(42 块) | ~253 s/it | 自研稀疏路径,gather + torch 反向重算 |
| SLA 开放竞争(29 块) | ~209 s/it | 少 13 块,比保护版快 ~17% |

**要点**:SLA 省的是理论计算量(95%),但本实现的稀疏路径(逐段 Python 循环、meanpool 打分、fp32 全尺寸反向重算)的单块开销远高于 FlashAttention,导致 wall-clock 反而比稠密慢。42→29 块的提速证明块数确实影响耗时,但固定开销仍占主导。这是当前实现"正确性优先"的代价,也是后续可优化的方向(算子化/并行化稀疏路径)。

---

## 7. 结论与下一步

1. **开放竞争下文本/音频信息部分存活但不可靠**:每行 2.4 块、57.6% 行失联;列保护能 100% 保住,代价是稀疏度 95.1%→92.9%。
2. **当前正在验证开放竞争训练的收敛性**:从 step-156 续训 156 步,若 loss 正常且推理不崩,说明模型可以适配"文本/音频块偶尔缺席"的稀疏模式;若效果差,回退列保护方案。
3. 候选后续:开放竞争 vs 保护版 ckpt 对比推理(768p,同 prompt)、proj_l 行为分析、稀疏路径算子优化。
